# Lessons

Running log of lessons learned, written as rules. Read at start of session, apply. Append new entries as they're learned.

- When dashboard data is mutated outside the API process, bridge the database to the browser with a server-owned live update channel (SSE or equivalent) and keep polling only as a fallback.
- When celebrations are driven by incoming rows, treat existing rows as the initial baseline and queue only unseen qualifying rows so multiple new messages play in order without replaying old wins.
- Treat `bucket.name` as the canonical profile bucket value; derive it from `dossier.dpd_bucket_id` through the `bucket` table instead of comparing raw bucket ids to `profiles.bucket`.
- Simulator setup/reset should leave persisted rows in `c_green.collections_messages` immediately; otherwise a browser reload correctly renders an empty dashboard until the next MySQL event tick.
- For live dashboard endpoints, select the small recent collection window first and then join reference tables; full-table dossier grouping can make the frontend appear empty while requests hang.
- Use `collections_messages.date_of_message_sent` for dashboard business-period filters such as daily/monthly KPIs and leaderboards; reserve `created_at` for ingestion/live recency.
- Anchor dashboard daily/monthly period filters to the latest loaded `date_of_message_sent` date, not wall-clock `CURDATE()`, so a new calendar day with no imported rows does not blank the TV dashboard.
- Keep every required design-system token inside the dashboard project and import the local copy; a sibling-folder CSS import makes the source tree non-portable even when the compiled bundle appears self-contained.
- Mask sensitive identifiers at the API response boundary and again at the UI render boundary; for LANs, use a fixed `••••` marker plus the final four characters and keep the complete masked token from wrapping so the redaction is readable, idempotent, and does not reveal the identifier's original length.
- Platform-conditional connection defaults must name the platform they are *for*, not the one they are against. `platform !== "win32" ? socket : tcp` silently forced every Linux container onto a macOS socket path and made `DB_HOST`/`DB_PORT` dead config; `platform === "darwin" ? socket : undefined` keeps the local-dev convenience without capturing production.
- Any credential file the app *writes* — not just reads — is a deployment constraint. `import_sheets.py` rewrites `token.json` every run and `server.ts` rewrites `token1.json` on refresh, so both need read-write mounts owned by the container uid. A `:ro` mount fails at refresh time, not at startup, so it survives a smoke test and dies in production.
- Before containerizing, check which build-time tools the *runtime* needs. Running TypeScript directly in production makes `tsx` a runtime dependency; leaving it in `devDependencies` breaks any image that prunes dev deps, and only at container start.
- When docs claim a script exists, verify it on disk before trusting the surrounding description. `CLAUDE.md`/`AGENTS.md` documented `simulate.py`, `populate_profiles.py`, `transfer_c_green_export.py`, and `DESIGN.md` long after they were deleted.
- Seed data containing real names or emails is PII, not fixtures: keep it out of version control (gitignore + out-of-band transfer) and say so in the file's own header, because whoever runs it is not the person who wrote the ignore rule. Ship the schema file committed and the data file separately.
- When handing over a lookup table, measure its join coverage against the fact table first. `emp_details` looked complete at 162 rows but matched only 113 of 167 agent emails, leaving a third of the leaderboard on a low-quality fallback — a data gap that would have been misread as a deployment bug.
- Read the existing fallback chain before describing what a missing join produces. The unmatched agents were never going to render as raw emails; `server.ts` already coalesced to the sheet's `agent_name`. The real defect was subtler and worse: inconsistent spellings, and one address carrying three different people's names.
- Structured identifiers beat hand-typed free text as a display source. Deriving names from `fname.lname@` local parts gave one deterministic spelling per address, where the manually maintained sheet column had drift and outright wrong names. Keep the authoritative roster ahead of both, so improving the roster silently improves the display.
- Verify containerized changes against *copies* of live credentials, never the originals. Mounting the real `token.json` into a test container makes the test rewrite a production token and can race with anything else refreshing it.
- Production-to-local seeders must treat the source as read-only, prove the target is local (and not the same server/schema), refuse populated targets by default, stream rows instead of loading the database into memory, and verify every copied table before reporting success; copied production PII stays local and must never become a checked-in fixture.
- When a seeder intentionally copies a table's schema but not its data, verify that the target table is empty and reset any source-carried auto-increment value; otherwise a successful-looking seed can retain stale rows or begin local identifiers at a production counter.
- When Vite and an API run as separate processes, do not assume Vite's `.env` loading configures the API. Load the environment file in the backend before constructing clients, and leave `NODE_ENV` unset in the local file so Vite can select development mode while the production image supplies production mode.
- Keep financial recovery totals separate from performance scores: display raw `amount_collected` as rupees for collection KPIs and transaction cards, while using weighted points only for rankings and celebration rules.
