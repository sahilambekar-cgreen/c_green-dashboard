# Lessons

Running log of lessons learned, written as rules. Read at start of session, apply. Append new entries as they're learned.

- When dashboard data is mutated outside the API process, bridge the database to the browser with a server-owned live update channel (SSE or equivalent) and keep polling only as a fallback.
- When celebrations are driven by incoming rows, treat existing rows as the initial baseline and queue only unseen qualifying rows so multiple new messages play in order without replaying old wins.
- Treat `bucket.name` as the canonical profile bucket value; derive it from `dossier.dpd_bucket_id` through the `bucket` table instead of comparing raw bucket ids to `profiles.bucket`.
- Simulator setup/reset should leave persisted rows in `c_green.collections_messages` immediately; otherwise a browser reload correctly renders an empty dashboard until the next MySQL event tick.
- For live dashboard endpoints, select the small recent collection window first and then join reference tables; full-table dossier grouping can make the frontend appear empty while requests hang.
- Use `collections_messages.date_of_message_sent` for dashboard business-period filters such as daily/monthly KPIs and leaderboards; reserve `created_at` for ingestion/live recency.
- Anchor dashboard daily/monthly period filters to the latest loaded `date_of_message_sent` date, not wall-clock `CURDATE()`, so a new calendar day with no imported rows does not blank the TV dashboard.
- Keep every required design-system token inside the dashboard project and import the local copy; a sibling-folder CSS import makes the source tree non-portable even when the compiled bundle appears self-contained.
- Mask sensitive identifiers at the API response boundary and again at the UI render boundary; for LANs, use a fixed `••••` marker plus the final four characters and keep the complete masked token from wrapping so the redaction is readable, idempotent, and does not reveal the identifier's original length.
- Platform-conditional connection defaults must name the platform they are *for*, not the one they are against. `platform !== "win32" ? socket : tcp` silently forced every Linux container onto a macOS socket path and made `DB_HOST`/`DB_PORT` dead config; `platform === "darwin" ? socket : undefined` keeps the local-dev convenience without capturing production.
- Any credential file the app *writes* — not just reads — is a deployment constraint. `import_sheets.py` rewrites `token.json` every run and `server.ts` rewrites `token1.json` on refresh, so both need read-write mounts owned by the container uid. A `:ro` mount fails at refresh time, not at startup, so it survives a smoke test and dies in production.
- Before containerizing, check which build-time tools the *runtime* needs. Running TypeScript directly in production makes `tsx` a runtime dependency; leaving it in `devDependencies` breaks any image that prunes dev deps, and only at container start.
- When docs claim a script exists, verify it on disk before trusting the surrounding description. `CLAUDE.md`/`AGENTS.md` documented `simulate.py`, `populate_profiles.py`, `transfer_c_green_export.py`, and `DESIGN.md` long after they were deleted.
- Seed data containing real names or emails is PII, not fixtures: keep it out of version control (gitignore + out-of-band transfer) and say so in the file's own header, because whoever runs it is not the person who wrote the ignore rule. Ship the schema file committed and the data file separately.
- When handing over a lookup table, measure its join coverage against the fact table first. `emp_details` looked complete at 162 rows but matched only 113 of 167 agent emails, leaving a third of the leaderboard on a low-quality fallback — a data gap that would have been misread as a deployment bug.
- Read the existing fallback chain before describing what a missing join produces. The unmatched agents were never going to render as raw emails; `server.ts` already coalesced to the sheet's `agent_name`. The real defect was subtler and worse: inconsistent spellings, and one address carrying three different people's names.
- Structured identifiers beat hand-typed free text as a display source. Deriving names from `fname.lname@` local parts gave one deterministic spelling per address, where the manually maintained sheet column had drift and outright wrong names. Keep the authoritative roster ahead of both, so improving the roster silently improves the display.
- Verify containerized changes against *copies* of live credentials, never the originals. Mounting the real `token.json` into a test container makes the test rewrite a production token and can race with anything else refreshing it.
- Production-to-local seeders must treat the source as read-only, prove the target is local (and not the same server/schema), refuse populated targets by default, stream rows instead of loading the database into memory, and verify every copied table before reporting success; copied production PII stays local and must never become a checked-in fixture.
- When a seeder intentionally copies a table's schema but not its data, verify that the target table is empty and reset any source-carried auto-increment value; otherwise a successful-looking seed can retain stale rows or begin local identifiers at a production counter.
- When Vite and an API run as separate processes, do not assume Vite's `.env` loading configures the API. Load the environment file in the backend before constructing clients, and leave `NODE_ENV` unset in the local file so Vite can select development mode while the production image supplies production mode.
- Keep financial recovery totals separate from performance scores: display raw `amount_collected` as rupees for collection KPIs and transaction cards, while using weighted RP only for rankings and celebration rules.
- Build container production dependencies from the lockfile in their own stage instead of pruning a dependency tree used by the frontend build; this makes the final runtime set explicit and prevents build-only packages from leaking into the image.
- When a KPI combines money and a weighted performance score, keep the rupee amount visually primary and show the score as a smaller bracketed secondary value with an explicit unit label such as `RP`.
- When rescaling a scoring system, apply one shared scale to every scoring path (stored bucket weights and derived Multiple Bucket bands), retain explicit business thresholds unless they are separately changed, and verify fractional multiplier formatting so values below one do not round to zero.
- When a development command runs Vite and a plain `tsx server.ts` process together, frontend HMR can make a change look partially deployed while the API still runs stale code; restart the backend and verify the API payload after every `server.ts` calculation change.
- A Vite production build is not a backend TypeScript validation step; container builds that ship `server.ts` through `tsx` should run `tsc --noEmit` explicitly before packaging the runtime image.
- An auth flow that writes to disk is a deployment constraint; one that reads an env var is not. Google's cached OAuth token forced a writable, uid-owned bind mount and a browser to mint it. Zoho's non-expiring Self Client refresh token deleted the mount, the `chown`, the rotation runbook, and let the ETL container run `read_only: true`. When choosing between integration auth styles, weigh what each one makes the container require, not just how the first call looks.
- Integrations are easiest to swap where the coupling is narrow, so check the seam before estimating. Migrating this ETL off Google looked large and was ~50 lines: the source vendor touched exactly one function, because everything downstream keyed off header names and communicated only through a database table. Measure the blast radius by grepping for the vendor, not by the size of the feature.
- A source migration is a schema migration in disguise. The replacement sheet renamed every header and encoded dates as numbers rather than strings — neither of which the old parser would have reported. Probe the real payload and print its headers, sample rows, and per-cell type interpretation *before* writing the mapping.
- Rank ingestion failure modes by whether they are loud. Missing headers silently produced zero imported rows and exit 0; an unparsed date silently loaded a row the dashboard then filtered out of every KPI. Both look like a healthy ETL in the logs. Make the first `sys.exit(1)` naming the mismatch and the second a counted `WARNING`, so neither can masquerade as success.
- Prefer extracting the value you want over sanitizing the string you were given. `re.sub(r"[^\d.\-]", "", "Rs. 5000.50")` leaves `".5000.50"`, which is not a float; `re.search(r"-?\d+(?:\.\d+)?", ...)` returns `5000.50`. Cleaning by deletion silently keeps whichever junk characters the character class happened to allow.
- Verify a numeric date-encoding guess against a computed constant, never a hand-derived one. A hardcoded spreadsheet serial in a test was two days off and produced a failure that looked like a code bug; deriving it as `(datetime(Y,M,D) - SPREADSHEET_EPOCH).days` tested the code instead of the arithmetic.
- One source column can carry more than one encoding, so parse defensively rather than from a single observed sample. The extractor wrote `date_of_message_sent` as epoch millis for some rows and as 12-hour day-first text for others in the same sheet; a probe of the first two rows saw only the numeric form, and the text rows silently loaded with NULL dates that no KPI could see. Sample across rows, not from the top.
- Never convert an epoch to a naive local datetime through the process's default timezone. `datetime.fromtimestamp(n)` yields IST in the Linux container and UTC on Windows, because Windows cannot parse an IANA name in `TZ` and falls back silently, so the same message lands 5.5 hours apart depending on where the ETL ran. Resolve the zone explicitly with `zoneinfo`, ship `tzdata` so it resolves everywhere, and warn rather than fail when it cannot.
- Look for a second column that already encodes the answer before trusting a timezone conversion. The sheet's `ai_processed_time` read `3/9/2026 12:53:08 PM` for the message whose epoch the ETL was storing as `07:23:01`, which settled the 5.5-hour question immediately and turned an assumption into a check.
- A failing assertion is a hypothesis about which side is wrong, not a verdict on the test. The epoch expectation "failed" because the code was right in production and wrong on the dev machine; correcting the test to match the buggy local behaviour would have locked in a real defect. Ask which environment the expectation was written from.
- Background processes do not outlive the session that started them. The ETL loop started for the user's live testing was reaped at session end, so new sheet rows stopped arriving and looked like an ingestion bug. Say plainly that a helper loop is session-scoped, and check whether it is still running before diagnosing anything downstream of it.
- Mark row ownership whenever two ingestion regimes share a table. Keeping the Google-era rows meant keeping rows whose content-derived `uid` can never appear in what the new source reports, making every one of them a permanent reconciliation candidate; a nullable `msg_id` both traces a row to its source message and scopes the sweep to rows this ETL actually owns. Scope the destructive query by ownership rather than trusting a heuristic guard to keep holding.
- Re-derive the safety margin after the premise changes, because a guard calibrated for one ratio silently expires. The 80% threshold looked like it protected the legacy rows, but it only held while the new source stayed small: `N < 0.8 x (4487 + N)` opens at ~17,948 rows, so the protection would have lapsed on an ordinary Tuesday months later. Solve the class of bug, don't tune the constant.
- Avoid semicolons inside SQL string literals in files other tools will execute. A semicolon in a `COMMENT` broke a naive statement splitter mid-literal and produced a syntax error pointing at valid DDL; the official client parses it fine, which is exactly what makes it a trap for whatever the operator actually uses. Prefer a dash.
- Probe the real payload before trusting a stakeholder's description of it. Asked whether the new sheet's headers matched, the answer was "different / renamed"; they were in fact the original Google-era names, and the identity mapping written on that answer was wrong in nine columns. The five-minute read-only probe settled in one run what the question could not — ask people about intent and policy, and the system about structure.
- An automated extractor upstream is a data source with its own failure modes, not a clean feed. The AI parser filling `Collection_Data` emitted the same employee code for two different agents and a loan number matching no dossier row. Since `emp_id` had just become the sole agent identity, a mis-parsed code silently credits the wrong person's leaderboard. Validate identity fields against the roster and report the mismatch rate rather than assuming extraction is correct.
- When a migration removes a field the old source supplied, look for it elsewhere before changing the consumer. Zoho reported `email_id` as the chat bot on every row where Google carried the agent's own address; recovering the real address from `emp_id` through `emp_details` inside the ETL kept `server.ts`, its six queries, and the whole leaderboard grouping untouched. Restore the contract at the boundary that broke it.
- Choose the fallback that fails into the widest identity space, not the nearest value. Writing the bot address when a code was unmatched would have merged every unresolved agent into a single leaderboard row; writing NULL lets the existing `COALESCE(empcode, email, agent_name, ...)` chain fall through to the person's name and still produce one entry each. A wrong shared default collapses distinctions; a null preserves them.
- Diagnose "the fix did not work" by proving which build answered, before doubting the fix. The dashboard filter looked broken until the port's owning PID turned out to predate the edit by an hour — a dev server already on 3001 was serving old code, and the retest belonged on another port rather than in the source. Check `Get-NetTCPConnection`/`lsof` process start time against the file mtime first.
- Key a row on identity, not on its contents, as soon as the source can edit records. A content-derived `uid` was correct while the sheet was append-only and became a double-counting bug the moment messages could be corrected: the edited row hashes differently, inserts as new, and orphans the original with no later run able to reconcile them. Hashing the upstream message id keeps an edit an `UPDATE`. Ask "can this record change after I first see it?" before choosing the key.
- A soft delete is only as good as the query that honours it, so count the read sites before choosing it. Marking rows `DELETED` needed the filter in all six `collections_messages` queries in `server.ts`; missing one would leave a retracted collection scoring on that panel alone — a bug that presents as a single wrong number, not as an obvious failure. Define the predicate once as a shared constant and grep the count.
- Soft delete also buys reversibility, which is what makes an automated reconciliation pass acceptable. Flagging rows the source no longer lists is self-healing (the row reappears, the next run clears the flag); hard-deleting them is not. Choose the destructive-looking feature only when the underlying operation is recoverable.
- Bound a reconciliation by the assumption it depends on, and write that assumption down. "Absent from the source means deleted" holds only while the source keeps all history; under a rotated or archived sheet the same logic hides every row outside the current window. Verify the retention model before enabling it, add a proportion guard so a partial fetch cannot read as a mass deletion, and ship a dry-run flag.
- A passing test can pass for the wrong reason. The dry-run assertion returned the expected 0 because the ratio guard fired first, so the dry-run branch was never executed — only the log line revealed it. When several guards can produce the same result, pick inputs that isolate the one under test, and assert the complementary case (same input, flag off) actually acts.
- Re-read a file immediately before editing it, not once at the start of a long session. `server.ts` had `CELEBRATION_MIN_RP` and an `RP_MULTIPLIER_SCALE` that the earlier read in the same session did not show, so an edit written from memory failed to match. Treat a stale read as a stale fact, and re-check anything quoted back to the user from it.
- Distinguish the vendor from the product when planning a migration. "Moving to Zoho" covered the sheet (the ETL data source) and Workspace identity (employee photos, via Admin Directory) — two independent integrations on different timelines. Migrate the one that was asked for and flag the other, rather than bundling them because they share a vendor name.
